Live Sensor Readings — Lifecycle & Interpretation

An Android (Java) walkthrough: capturing live light-sensor data, managing the sensor listener through the Activity lifecycle, smoothing readings with EMA, and interpreting three controlled observations.

👤 Patrick Kilonzo Mbithi🆔 SCT211-0036/2024🎓 BSc Computer Science👨‍🏫 Dr. Lawrence Nderu

1 · Lab Objective

The goal of this lab is to build an interactive Android screen that acquires live data from the device’s light sensor (Sensor.TYPE_LIGHT), manages the listener registration across the Activity lifecycle, applies exponential moving average (EMA) smoothing, records three controlled observations (covered, indoor light, flashlight), and generates a written analysis of the results. By the end of this lab the app can:

🔲Detect sensorChecks for TYPE_LIGHT availability; disables controls gracefully when missing.
⚡️Lifecycle-aware listenerRegisters in onResume, unregisters in onPause to avoid background battery drain.
📈Live EMA smoothingApplies St = α·rawt + (1-α)·St-1 with α=0.3 to suppress jitter.
📝Record observationsThree buttons capture raw + smoothed values with timestamps for later analysis.
💡Generate interpretationProduces a structured report covering pattern, confounding factors, sampling, battery, and smoothing trade-offs.

2 · How the App Works

The user journey is a single screen with a clear sequence: verify sensor → start listener → watch live values → record three conditions → generate analysis.

Launch app→Sensor check→Available? Register listener→Live EMA updates→Cover sensor → Record #1
Indoor light → Record #2→Flashlight → Record #3→Generate Analysis→Interpretation report
Rotate / background→ViewModel + savedInstanceState retain data→onResume re-registers listener

Project Structure

app/ ├─ src/main/java/…/MainActivity.java ← logic (Sections 4–6) ├─ src/main/res/layout/activity_main.xml ← UI (Section 3) ├─ src/main/res/values/themes.xml ← MaterialComponents theme └─ src/main/res/values/colors.xml ← custom color attrs (optional)

⚠️ Watch out. The app theme must inherit from Theme.MaterialComponents (e.g., Theme.MaterialComponents.DayNight.DarkActionBar) for CardView, TextInputLayout, and ?attr/colorPrimary to resolve. A plain AppCompat theme will crash on inflation.

3 · User Interface (activity_main.xml)

The whole form sits inside a ScrollView → LinearLayout so the on-screen keyboard never hides content. Each card is a self-contained section explained below, then the complete file is shown at the end of the section.

3.1 Header & Experiment Question

A title, subtitle, and a CardView containing the experiment question give context before any data appears.

3.2 Sensor Information Card

Four TextView pairs (label + value) show sensor name, unit, availability status, and data source. Values are populated at runtime in checkSensorAvailability().

Shows raw lux, EMA-smoothed lux, timestamp, and a horizontal ProgressBar (max 10,000 lux). All values are updated on the UI thread from onSensorChanged.

Displays current listener state (Registered / Unregistered) and the current Activity lifecycle phase. Two buttons allow manual register/unregister; the app also auto-registers in onResume and auto-unregisters in onPause.

3.5 Observation Table Card

A TableLayout with three fixed rows (Covered, Indoor Light, Flashlight) and four columns (Condition, Raw, Smoothed, Timestamp). Below the table, three colored buttons let the user record each observation.

3.6 Analysis & Interpretation Card

A TextView (tvAnalysis) holds the generated report. A centered button triggers generateAnalysis().

4 · Activity Logic (MainActivity.java)

The Activity implements SensorEventListener and coordinates four concerns: sensor setup → lifecycle-aware registration → EMA smoothing → observation recording & analysis.

4.1 Imports and Member Fields

Key fields include the SensorManager, Sensor, ViewModel, all UI references, listener state flag, EMA state, and three Observation objects.

4.2 onCreate(): Binding Views, ViewModel, Sensor, and State Restoration

Initializes EdgeToEdge, binds views with null-checks, creates the ViewModel, obtains the light sensor, wires click listeners, checks sensor availability, and restores saved instance state.

4.3 Sensor Availability Check

If the light sensor is missing, the UI shows Unavailable, disables all controls, and displays a Toast. Otherwise it populates the sensor name, version, unit, and status.

4.4 Register / Unregister Listener

registerListener() uses SENSOR_DELAY_NORMAL (~200 ms). A boolean flag prevents duplicate registration. unregisterListener() cleans up and updates UI. Both update tvListenerState and button enabled states.

4.5 SensorEventListener: onSensorChanged & onAccuracyChanged

onSensorChanged receives raw lux, applies EMA smoothing (α=0.3), updates all UI elements on the main thread, clamps the progress bar to 10,000 lux, and saves the latest values to the ViewModel for rotation survival. onAccuracyChanged updates the data source label color when accuracy drops to UNRELIABLE.

⚠️ Watch out. SensorEventListener callbacks run on a sensor thread, not the main thread. Always wrap UI updates in runOnUiThread() or use Handler/LiveData. The code above guards every view reference with null-checks to survive layout mismatches.

4.6 Lifecycle Methods: Visible-Lifecycle Registration

The app follows the visible lifecycle pattern: register in onResume, unregister in onPause. This prevents background battery drain and duplicate listeners after rotation. onDestroy adds a final safety cleanup. Each phase logs to tvLifecyclePhase for debugging.

4.7 Recording Observations

Each Record button calls recordObservation(n) which reads the current raw/smoothed values from the UI, timestamps them, and stores them in the corresponding Observation object. The table row is updated immediately.

4.8 Generating the Analysis Report

generateAnalysis() builds a structured string covering: confirmation of three observations, raw/smoothed values per condition, pattern interpretation (monotonic increase expected), confounding factors (calibration, spectral response, cosine error, temperature, casing), sampling & timing notes (requested vs actual rate, batching, no hardware timestamp), battery cost estimates, and EMA smoothing trade-offs. It concludes with a lifecycle behavior summary.

4.9 State Persistence: onSaveInstanceState & restoreState

Saves hasFirstReading, smoothedValue, and all three observations into the Bundle. On restore, re-populates the UI and observation objects. The ViewModel additionally retains the latest raw/smoothed values across configuration changes.

4.10 ViewModel for Rotation Survival

A minimal ViewModel holds the last raw reading, last smoothed value, and the hasFirstReading flag. It survives configuration changes (rotation) so the live values don’t reset when the Activity is recreated.
